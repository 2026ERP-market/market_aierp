# 백엔드 담당자에게 전달할 API 연동 작업 지시

> 최신 요구사항은 'AI 추천에서 수량 수정 → 발주하기/발주 안 함 → 내역 → 입고'입니다. 별도 초안 작성과 자동 발주는 이번 범위에서 제외합니다. 아래 초안 중심 제안은 이전 검토 기록이며 신규 구현 기준은 [DIRECT_ORDER_API.md](./DIRECT_ORDER_API.md)를 우선하세요. 최신 팀원 코드의 상품 저장·실사·공급사별 발행·입고는 보존했습니다. 개별 발주에는 선택 추천 하나의 원자적 발행·원래 AI 수량 보존·멱등성 계약이 필요합니다.

## 요청 배경

Expo 모바일의 POS UI와 Mock 업무 흐름은 구현되어 있습니다. 이번 프론트엔드 작업에서는 저장소의 FastAPI 코드를 기준으로 조회/AI HTTP 어댑터와 응답 검증을 추가했습니다. 공유 기준은 AI 통합 및 백엔드 테스트가 포함된 feat/pos-ui-backend의 94cc14b입니다. 팀원의 백엔드 변경을 그대로 보존했으며 프론트 담당자가 백엔드 코드를 수정하지 않았습니다. 프론트 담당자의 PC에는 백엔드·DB 실행 환경이 없으므로 실제 서버 연결 성공은 미검증입니다. 백엔드 설치·실행은 하지 않았습니다.

**아래 서버 작업을 완료하고, 프론트 담당자에게 접속 가능한 API 주소·OpenAPI·테스트 결과를 전달해 주세요.** Mock 화면이 보인다는 것은 실제 ERP 연결 성공을 의미하지 않습니다.

## 1. 실행 가능한 서버와 접속 정보 제공 — B 담당

- PostgreSQL 스키마/마이그레이션, 재현 가능한 개발 데이터, FastAPI 실행 방법을 정리해 주세요. 실제 고객 개인정보나 운영 키를 Git에 포함하지 마세요.
- Android 휴대폰에서도 접속 가능한 서버 주소를 제공해 주세요. 휴대폰의 localhost는 휴대폰 자신이므로 PC/개발 서버의 LAN 주소 또는 배포 주소가 필요합니다.
- `/health`, `/docs`, `/openapi.json`과 아래 조회 endpoint가 DB 연결 상태에서 동작하는지 확인해 주세요. 현재 `/health`는 고정 healthy 응답이어서 DB 준비 여부를 증명하지 못합니다. 준비 상태 확인 방법도 제공해 주세요.
- Expo 웹의 개발 origin 허용과 인증 방식/토큰 전달 계약을 정해 주세요. 인증된 사용자/역할/매장 접근 권한은 서버에서 검증해야 합니다. 모바일의 warehouse_id 환경변수는 권한 증명이 아닙니다.
- API 키·DB 비밀번호·토큰 서명 키를 EXPO_PUBLIC 환경변수로 전달하지 마세요. 앱에 들어가는 설정은 공개됩니다.

## 2. 프론트에서 연결 준비한 현재 API

| 기능 | 현재 프론트 요청 | 비고 |
| --- | --- | --- |
| 대시보드 | GET /api/v1/dashboard/summary?warehouse_id=WH-ASAN | 매장명·서버 날짜·지표·브리핑 |
| 재고/상품 | GET /api/v1/inventory/current?warehouse_id=WH-ASAN | 목록과 상품 상세 재사용 |
| AI 추천 | GET /api/v1/purchases/recommend?warehouse_id=WH-ASAN | 현재 GET 내부에서 추천 생성·DB 저장 가능 |
| 발주 조회 | GET /api/v1/purchases/orders | 현재 매장 필터가 없어 WH-ASAN 외의 모바일 발주 조회는 차단 |
| 판매 참고 | GET /api/v1/sales/summary?days=N | 오늘까지의 기간만 지원, 응답 start/end 검증 |
| AI 질문 | POST /api/v1/agent/chat?warehouse_id=WH-ASAN | JSON: {"message":"질문"}, 구조화 액션 검증 |

프론트는 서버 응답을 변환/검증하고 오류·재시도·빈 배열을 처리합니다. 잘못된 JSON, 숫자 대신 문자열, 허용되지 않은 상태/AI 이동 경로는 오류로 처리하며 Mock으로 자동 전환하지 않습니다. 읽기 요청 취소와 타임아웃, HTTP 401/403/409/500도 구분합니다. 테스트의 HTTP 응답 fixture는 실제 서버 응답을 확인한 결과가 아닙니다.

추천 조회가 DB를 변경하므로 프론트는 같은 화면의 대시보드 완료 후 추천을 조회하고 중복 요청을 공유합니다. 이것만으로 여러 사용자/기기의 동시 생성은 보호할 수 없습니다. 서버에서 멱등성·동시성 제어가 필요합니다.

## 3. 발주 업무 흐름 합의 — B·A, 추천은 C 협의

**현재 모바일:** 추천 → 초안 생성 → 수량 저장 → 별도 승인 → 입고 내역 확인.

**현재 서버:** 추천 액션(approve/modify/reject) → 승인된 추천을 공급사별로 발주서 발행.

두 흐름은 동일하지 않습니다. 다음 중 실제 프로젝트 업무 흐름을 합의하고 OpenAPI를 확정해 주세요.

- 모바일의 초안 흐름을 서버에 제공할지, 모바일 UI를 서버의 추천 검토/발주 발행 흐름으로 변경할지 결정.
- 초안/추천 ID와 발주서 ID 관계, 상태 전이, 수량 저장·승인·발행의 구분, 허용 작업/권한, 취소 및 재시도 규칙 명시.
- 상품 등록/수정에 필요한 식별자와 바코드 계약, 재고 실사의 기록/실제 조정 구분, 로트 지정과 입고 등록 요청 계약 명시.
- 합의 전 프론트에서 상품 저장·실사·초안 생성·수정·승인을 기존 서버의 다른 POST로 대체하지 않습니다. 현재 API 모드에서는 이 쓰기 작업들을 차단합니다. AI 질문 POST만 연결합니다.

## 4. 발주·입고 정확성 보완 — B 담당

- `replenishment_service.py`의 입고 처리는 현재 요청 시작 시 received로 바뀝니다. 빈 요청·부분입고·완료입고·기존 상태를 검증하고 남은 수량으로 partial/received를 판정해 주세요.
- 음수/초과 수량, 존재하지 않는 line_no, 중복 품목, 잘못된 소비기한, 이미 완료/취소된 발주 재처리를 거부해 주세요. received_items의 list[dict] 대신 검증 가능한 품목 스키마를 제공해 주세요.
- 반복 요청/동시 요청의 중복 발주·중복 입고를 막고, 발주/추천/로트 ID 충돌을 방지해 주세요. 여러 테이블 변경은 원자적으로 처리하고 실패 시 상태/재고를 보존해 주세요.
- 발주서의 소속 매장을 저장/검증하고 추천 조회·입고 예정 수량 집계·발주 발행을 해당 매장으로 제한해 주세요. 입고 매장을 WH-ASAN으로 고정하지 마세요.
- 추천 승인/수정은 현재 상태·권한·수량을 검증하고, 부적절한 상태 변경과 중복 발행을 거부해 주세요. 가능하면 401/403/404/409/422 등 원인에 맞는 오류 계약을 제공해 주세요.

## 5. 필요한 데이터 보완 — B·C·D 담당

- B: 바코드, 상품별 판매 실적/이동 이력, 발주 품목명, 실제 입고 일시/부분입고 내역, 매장 필터, 상품 수정·실사 계약.
- B: 대시보드의 오늘 매출이 0일 때 과거 매출로 대체하는 현재 동작을 구분해 주세요. 실제 기준일·집계 기간·갱신 시각을 응답에 명시해 주세요.
- C: 추천 ID/상태, 예측 기간·단위, 실제 계약 매입가·납기, 과잉 위험/판정 근거, 모델 출처와 데이터 부족 상태를 명시해 주세요. 최신 코드는 모델명을 dow-seasonal-v1로 표시하고 최근 판매 기반 평균에 학습된 요일 계수, 포아송 예측구간, 서비스수준 기반 안전재고를 적용합니다. 계수의 학습 출처는 코드 주석에 기재되어 있으나 운영 매장 데이터로 재학습한 결과나 학습 성능 수치를 프론트에서 별도로 검증한 것은 아닙니다. 과거 저장 예측과 신규 추론 결과의 모델 버전·기준일을 구분해 주세요.
- D: 현재 agent_service는 키워드 분기 방식입니다. LLM 연동 여부·모델/응답 출처·오류 계약을 명시하고 임의 문자열로 발주·입고 작업을 실행하지 마세요. 구조화 액션은 허용된 ERP 대상/식별자만 반환해 주세요.

현재 프론트는 없는 수치를 0이나 샘플로 만들지 않습니다. 예산/최근 판매/예측 근거/시각 등 미제공 필드는 null 또는 명시적 미제공 상태로 처리합니다. 서버 응답에 승인 권한이 없으므로 allowedActions는 비어 있습니다. 기존 발주 응답을 임의로 수정/승인 가능한 초안으로 해석하지 않습니다.

## 6. 전달 및 완료 기준

1. 서버 주소, 실행 방법, 정확한 OpenAPI, 요청/응답 예제와 인증/매장 규칙 제공.
2. 실제 DB 기반 정상·빈 목록·잘못된 요청·권한 오류·부분/완료 입고 테스트 결과 제공.
3. 중복/동시 발주·입고, 실패 시 롤백과 상태 보존 검증.
4. A와 함께 모바일 API 모드로 조회 → 계약에 맞는 업무 변경 → 재조회 → DB 반영 확인.

프론트 전환 설정은 mobile/.env.local에 EXPO_PUBLIC_DATA_SOURCE=api, EXPO_PUBLIC_API_BASE_URL=접속가능한서버루트주소, EXPO_PUBLIC_WAREHOUSE_ID=WH-ASAN을 넣고 Expo를 재시작하는 방식입니다. 실제 주소를 받기 전에는 mock을 유지합니다. 백엔드 및 main 브랜치 변경·배포는 담당자/팀 리뷰로 진행해 주세요.

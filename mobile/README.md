# 재고·발주 중심 모바일 프론트엔드

현재 주제는 **개인 운영 중소형 마트의 재고·발주 최적화를 위한 모바일 ERP 기반 AI 에이전트**입니다. 종합 ERP·회계·세무·인사·CRM은 핵심 범위에서 제외합니다. 루트 README와 공통 docs에는 이전 5개 탭·개발 단계 기록이 남아 있습니다. 이번 수정은 mobile/로 제한했으므로 현재 화면 구성은 이 문서를 기준으로 확인하세요. 공통 문서 정합성 반영은 팀 협의 항목입니다.

## 실행

```powershell
cd mobile
npm ci
npm run web -- --port 8081 --offline
```

브라우저 주소는 http://localhost:8081 입니다. 터미널의 서버를 유지해야 합니다. 이미 의존성이 설치되어 있으면 npm ci는 생략합니다. 실기기는 동일 Wi-Fi의 호환 Expo Go에서 `npm start`로 확인합니다. Android/iOS 실기기 동작을 검증 완료했다는 뜻은 아닙니다.

## 사전 분석과 재구성 계획

기존 화면은 5개 탭(홈·매출·재고·발주·AI), 매출 KPI 중심 홈, 상품 상세와 수량 수정/승인 화면, 고정 AI 데모 응답이었습니다. 매출 화면은 `SalesService`에 의존하며 다른 업무 처리 서비스와 분리되어 있었습니다. 상품 입력·실사·발주 승인 핸들러는 재사용 가능합니다. 입고 예정·판매량 추세·과잉 위험·추천에서 신규 초안 생성은 없었습니다.

진행 순서는 다음과 같습니다.

1. 매출 화면을 삭제하지 않고 루트 스택의 보조 화면으로 이동하고 하단 탭을 4개로 구성.
2. 홈의 매출 KPI 대신 발주 추천·위험·승인 대기를 배치하고 상세로 바로 이동.
3. 재고에 입고 예정·판매 추세·소비기한·과잉 위험을 표시.
4. 발주 추천 → 명시적 초안 생성 → 수량 수정·저장 → 확인 후 승인 → 입고 내역 조회 연결.
5. AI 질문을 재고/발주로 좁히고 허용된 상품·발주 상세와 초안 생성 액션 연결.

| 화면 | 내용 |
| --- | --- |
| 홈 | 오늘 검토할 추천, 부족/품절·소비기한·과잉 위험, AI 발주 브리핑, 승인할 초안, 상품/발주 상세 이동 |
| 재고 | 상품명/바코드 검색, 분류·위험 필터, 현재/입고 예정/최근 판매 수량, 상품 입력 경로 |
| 상품 상세 | 기존 가격·공급업체·배치별 소비기한·입출고·실사, 판매량 추세, 추천 발주 연결 |
| 발주 | AI 추천, 공급업체 필터, 예산/예상 금액, 초안 생성, 승인 검토 대기, 발주·입고 내역 |
| 발주 상세 | 추천 근거·예상 수요·납기·단가, 수량 수정, 미저장 예상 금액, 저장 후 승인, 입고 내역 조회 |
| AI | 품절·과잉·추천량·초안 요청, 구조화 카드, 발주 상세 및 확인 후 데모 초안 생성 |
| 판매 데이터 참고 | 기존 `/sales` 화면 유지. 재고 하단의 보조 버튼으로 접근. 메인 탭에서는 분리 |

매출 화면 구현, 기존 `services/contracts.ts`, 기존 `types/domain.ts`는 이번 변경 전과 파일 해시가 동일합니다. 매출 라우트 파일은 app/(tabs)/sales.tsx에서 app/sales.tsx로 이동하며 상대 import 경로만 조정했습니다. `/sales` URL은 유지됩니다.

## 실제 데이터와 Mock 경계

모든 화면은 기존 Mock/API 표시를 유지합니다. 초기 데이터는 고정 샘플이며 모델을 실행하지 않습니다. 신규 제안 `ReplenishmentService`는 기존 6개 서비스 계약을 대체하지 않습니다. 추천 수량과 예상 수요는 고정 fixture를 읽고, 프론트엔드가 최적화·위험 판정 알고리즘을 계산하지 않습니다. 비용 합계만 단가×수량으로 표시합니다. 미제공 단가는 0으로 대체하지 않습니다.

- `services/replenishment.ts`: 입고 예정·판매량 추세·과잉 위험·추천·예산 데이터와 초안 생성 인터페이스 **제안**.
- `services/mock/replenishment-data.ts`: 초기 추천/계획 fixture. 예산 100,000원, 추천 합계 88,000원은 데모 정보.
- 기존 mock 서비스의 메모리에 신규 초안을 넣어 기존 발주 상세·수량 저장·승인으로 이어집니다.
- 같은 추천의 중복 초안 생성은 방지합니다. AI 질문만으로 초안이 생성되거나 발주가 승인되지 않습니다.
- 추천 카드에서 확인창을 거쳐 생성한 뒤에도 초안 상태이며 실제 발주를 전송하지 않습니다.
- 승인 실패는 기존 상태를 유지합니다. 승인만으로 재고를 증가시키지 않습니다.
- 입고 예정 수량은 현재 재고와 별개입니다. 입고 등록·DB 반영은 서버 연동 준비 중이며 현재는 입고 내역 조회만 제공합니다.
- 예산 초과는 검토 경고입니다. 서버에 없는 승인 조건을 프론트엔드에서 새로 강제하지 않습니다.
- API 모드에는 신규 계획 서비스도 `contract_pending`을 반환합니다. 오류 시 Mock으로 자동 전환하지 않습니다.
- AI 액션은 허용된 경로/식별자를 검증하며 임의 URL·문장·코드를 실행하지 않습니다. 기존 AgentAction 계약은 보존하고, Mock에서만 선택적 UI 메타데이터를 제공합니다.

## 팀원과 협의할 항목

| 담당 | 확인할 계약 |
| --- | --- |
| B ERP/DB | 입고 예정량, 배치·소비기한, 발주 ID/상태/권한/버전, 초안 생성과 입고 처리 |
| C 예측/추천 | 예측 기간·수량·단위·근거, 부족/과잉 판정, 납기·기존 입고 예정 반영, 추천 ID |
| D 에이전트 | 발주 질문 범위, 구조화 카드, 검증 가능한 ERP 액션, 초안 생성 전 사용자 확인 |

새로운 HTTP endpoint를 임의로 확정하지 않았고 B/C/D의 서버·DB·엔진 코드를 수정하지 않았습니다. 인증·개인정보·토큰 보관 기능도 변경하지 않았습니다.

## POS 스타일 홈 — 이번 디자인 적용 범위

이번에는 홈부터 변경했습니다. 긴 추천 카드 앞에 큼직한 2×2 업무 버튼과 승인 대기·품절/부족·소비기한 위험을 배치합니다. 기존 추천 카드·AI 브리핑·소비기한 상세·승인할 발주서는 아래에 유지합니다. 홈의 조회 Promise.all, 서비스 호출, waiting 판정, Mock/API 분리, 초안 생성과 승인 로직은 변경하지 않았습니다.

| 업무 버튼 | 실제 연결 |
| --- | --- |
| AI 발주 추천 | /purchases?view=recommendations |
| 재고 확인 | /inventory?status=all |
| 상품 입고 | /purchases?view=orders — 기존 발주·입고 내역 조회, 입고 등록은 준비 중 |
| 소비기한 관리 | /inventory?status=expiring |

홈에서는 실제 입고를 수행하지 않습니다. 새 입고 입력 화면·입고 API·POS 결제·상품 판매 기능을 추가하지 않았습니다. 승인 대기는 기존 allowedActions, 위험 숫자는 기존 서비스 응답을 사용합니다. 로딩 중 임의의 숫자를 생성하지 않습니다.

### 재사용 기준과 다음 화면 설계

- `src/theme/pos.ts`: POS 전용 색·간격·모서리·터치 높이 토큰. 기존 기본 테마는 유지합니다.
- `PosHomeActions`: 2열 업무 버튼과 코드로 그린 간단한 아이콘. 별도 이미지/아이콘 라이브러리가 필요하지 않습니다. 작은 화면에서는 문구 크기와 길이를 조정하며 텍스트를 잘라 숨기지 않습니다.
- `PosWorkQueue`: 색과 명확한 라벨·수치를 함께 사용하고, 각 상태 목록으로 연결합니다.
- `Screen variant="pos"`: 홈에서만 간격과 샘플 안내를 간결하게 표시합니다. 기본값 standard인 기존 화면은 이전 스타일을 유지합니다. Card·Button·ResourceState·기존 추천/발주 카드를 그대로 재사용합니다.
- **재고 후속안:** 상단 바코드 텍스트 검색 + 상품명/바코드/현재고/입고 예정/위험의 목록형 행. 수천 개 상품은 FlatList 가상화와 서버 검색/페이지네이션 계약을 검토합니다. 기존 ScrollView에 대량 행을 그대로 넣는 방식으로 확장하지 않습니다. 카메라 스캔은 이번에 추가하지 않습니다.
- **발주 후속안:** POS 장바구니처럼 상품별 수량 입력·단가·소계를 묶고 하단에 합계와 저장/승인을 구분합니다. 미저장 승인 차단, 중복 요청 방지, 서버 성공 후 갱신, 실패 시 편집값 유지 조건을 보존합니다. 가상 결제 UI는 만들지 않습니다.
- **입고 후속안:** 바코드 확인 → 발주 품목 매칭 및 실제 수량 입력 → 확인. 입고 수량·소비기한 배치·버전/멱등성·권한·재고 반영은 B의 공식 API 계약이 필요합니다. API 준비 전에는 등록을 비활성화하거나 명시적 데모로만 제공합니다.
- **AI 후속안:** 기존 추천 카드의 수량·근거·예상 금액을 유지하고, 사용자 확인 후 ERP 초안으로 연결합니다. AI 문장만으로 생성/승인/입고하지 않습니다.

이번 변경 파일은 `DashboardScreen.tsx`, `components/common/ui.tsx`, 신규 `components/pos/PosHomeActions.tsx`, 신규 `theme/pos.ts`, 이 문서입니다. 나머지 재고·발주·입고 화면 디자인은 아직 변경하지 않았습니다. 서비스·API 계약·Mock·상태 훅·백엔드는 변경하지 않았고 패키지를 설치하지 않았습니다.

Expo 웹 개발 서버의 HTTP 200과 실제 화면 실행을 확인했습니다. 기존 Edge로 320/390/768/1280px에서 2×2 배치·터치 크기·가로 넘침 없음, 네 업무 버튼·세 업무 대기 바로가기, 기존 입고 상세 조회, 빈 목록·권한 오류·정상 복귀를 확인했습니다. 브라우저 런타임 예외와 실제 /api/ 호출은 없었습니다. 화면 이동 검사는 비활성 홈의 보존된 텍스트 대신 재고 목록의 조회 완료를 기다리도록 보완한 뒤 통과했습니다. Android/iOS 실기기와 시스템 큰 글꼴·스크린 리더는 미검증입니다. 스크린샷과 로컬 브라우저 검사 파일은 .test-build/ 아래 Git 제외 상태입니다.

## 백엔드 브랜치 위에 POS UI 결합

`feat/pos-ui-backend`는 백엔드 담당자의 `origin/feat/back` 커밋 `ec82112` (`back v0.9`)에서 만든 독립 통합 작업 브랜치입니다. 기존 `feat/mobile-ui-review`, 원격 feat/back 및 main을 직접 변경하지 않고 이 통합 브랜치만 공유합니다.

백엔드 브랜치는 우리 모바일 커밋 55ff892를 이미 포함하며, mobile의 차이는 package.json의 `dev: expo start --web` 추가뿐이었습니다. 이 명령을 포함한 백엔드 측 변경을 그대로 보존하고, POS 홈·공통 화면 옵션·신규 POS 컴포넌트/테마·문서만 작업 트리에 유지했습니다. 충돌은 발생하지 않았습니다.

전환 전 수정/새 파일 10개를 `.test-build/pos-integration-nDbrbK/`에 백업하고, 전환 직후 SHA-256이 모두 동일한 것을 확인했습니다. 여기에는 기존 로컬 README/docs도 포함됩니다. 이 백업은 로컬용이며 Git에서 제외됩니다.

**현재 연결 상태:** 백엔드 소스가 같은 브랜치에 있다는 것과 Expo 모바일의 실제 API 연결 완료는 다릅니다. feat/back의 루트 Vite 앱은 재고 API 연동 코드를 갖고 있지만, mobile의 live 어댑터는 여전히 contract_pending 상태이고 기본값은 mock입니다. 새로 받은 FASTAPI_BACKEND_SPEC.md와 실제 응답을 바탕으로 모바일 필드 매핑·검증·인증/권한을 합의하고 연결하는 작업은 별도입니다. 실제 주문·입고·DB 저장을 성공한 것으로 표시하지 않습니다.

백엔드/DB/Docker/루트 Vite 연동 코드와 mobile 서비스·타입·훅·의존성은 origin/feat/back과 동일한 것을 diff로 확인했습니다. Python/npm 패키지 설치, AI 모델 다운로드, DB/Docker/백엔드 서버 실행은 하지 않았습니다. 현재 개발 서버는 꺼져 있어 다시 확인하려면 mobile에서 `npm run web`을 실행합니다. 타입 검사·ESLint와 기존 서비스 테스트 19개는 통과했습니다. 실제 백엔드 실행·모바일 API 통신·실기기는 미검증입니다.

통합 후 `npm run build:web`도 성공했습니다. Expo 웹 export 결과는 dist/에 생성되며 Git에서 제외됩니다. 이 성공은 Python 백엔드·DB·실제 API 연동 검증을 의미하지 않습니다.

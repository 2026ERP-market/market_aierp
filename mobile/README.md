# 재고·발주 중심 모바일 프론트엔드

## 최신 추가: AI 자동 발주 UI와 Mock 실행

공유 기준: 원격 `4d7f547`의 직접 발주 API·모바일 연결·팀원 테스트를 먼저 반영했습니다. 아래 과거의 상품별 발주 미연동 설명은 당시 기록이며 현재 직접 발주 구현과 구분하세요. **자동화 설정·서버 작업자는 여전히 미연동**입니다. 실제 서버 통신 검증은 별도로 필요합니다.

상단 `자동 발주` 토글과 설정 화면에서 모드를 확인합니다. Mock은 기본 OFF이며 최초 ON 확인 후 현재 미처리 샘플 추천을 개별 승인 없이 발주합니다. 결과·오류·제외 사유와 내역 링크를 제공하며 발주만으로 현재 재고를 늘리지 않습니다. OFF는 다음 추천부터 중단하며 이미 진행 중인 요청이나 발주를 취소하지 않습니다. 중복 처리된 추천과 거절한 추천을 다시 발주하지 않습니다.

실행은 메모리 데모이며 ON 시 한 번 처리합니다. 설정 창의 `샘플 추천 이벤트 재실행 / 재시도`로 이벤트와 재시도를 재현하세요. 샘플 주의 문구가 있는 추천도 데모로 처리하므로 실제 위험/예산 정책 검증이 아닙니다. 앱 재시작 시 OFF이고 앱이 닫힌 동안 실행되지 않습니다. 샘플 데이터 표시는 계속 유지합니다. **실제 API 모드는 자동화 상태 미확인·연동 준비로 토글이 비활성화되며 서버 설정/발주 요청을 보내지 않습니다.** 기존 실제 조회·수동 기능은 유지합니다.

백엔드 담당자에게 [AUTOMATION_BACKEND_HANDOFF.md](./AUTOMATION_BACKEND_HANDOFF.md)를 전달하세요. 서버 설정·권한·추천 이벤트 작업자·멱등 발주·운영 정책·내역·테스트 요구사항과 아직 존재하지 않는 제안 API를 구분했습니다. 현재 UI/Mock 완성이 실제 자동 발주 서버 구축 완료를 뜻하지 않습니다. 아래 이전 절의 '자동화 미구현' 문구는 이전 작업 당시 기록입니다. 신규 의존성은 없습니다.

## 모바일 홈 상품 영역 및 발표용 확인

950px 미만에서는 분류·검색·상품 카드·업무 메뉴를 하나의 FlatList 안에서 세로 스크롤합니다. 기존 고정 업무 메뉴가 상품 목록의 높이를 차지해 아래쪽 카드가 잘리던 문제를 해결했습니다. 상품 열 수는 실제 목록 영역의 너비로 계산하며, 휴대폰에서는 기본 2열로 표시합니다. 기본 업무 6개 외 메뉴는 `추가 업무 6개 보기`로 펼칠 수 있습니다. 작은 화면과 가로 방향에서는 아래로 스크롤해 나머지를 확인하세요. PC의 상품/발주 패널 좌우 배치와 검색·필터·페이지 이동·발주 로직은 유지합니다.

`npm run web -- --port 8081` 실행 후 `http://localhost:8081/`에서 브라우저의 모바일 화면 모드(예: 390×844)로 확인하거나, `npm start`의 QR로 Expo Go에서 확인합니다. 기본 Mock 모드의 샘플 표시를 유지한 채 발표 자료를 촬영하세요. 웹 모바일 화면 검사는 실제 Android/iOS 화면 검사를 대신하지 않습니다. 로컬 캡처와 검사 스크립트는 Git 제외 경로인 `.test-build/`에 보관하며 의존성은 추가하지 않습니다.

## 사전 분석과 재구성 계획

기존 화면은 5개 탭(홈·매출·재고·발주·AI), 매출 KPI 중심 홈, 상품 상세와 수량 수정/승인 화면, 고정 AI 데모 응답이었습니다. 매출 화면은 `SalesService`에 의존하며 다른 업무 처리 서비스와 분리되어 있었습니다. 상품 입력·실사·발주 승인 핸들러는 재사용 가능합니다. 입고 예정·판매량 추세·과잉 위험·추천에서 신규 초안 생성은 없었습니다.

진행 순서는 다음과 같습니다.

1. 매출 화면을 삭제하지 않고 루트 스택의 보조 화면으로 이동하고 하단 탭을 4개로 구성.
2. 홈의 매출 KPI 대신 발주 추천·위험·승인 대기를 배치하고 상세로 바로 이동.
3. 재고에 입고 예정·판매 추세·소비기한·과잉 위험을 표시.
4. 발주 추천 → 명시적 초안 생성 → 수량 수정·저장 → 확인 후 승인 → 입고 내역 조회 연결.
5. AI 질문을 재고/발주로 좁히고 허용된 상품·발주 상세와 초안 생성 액션 연결.

## 실제 데이터와 Mock 경계

모든 화면은 기존 Mock/API 표시를 유지합니다. 초기 데이터는 고정 샘플이며 모델을 실행하지 않습니다. 신규 제안 `ReplenishmentService`는 기존 6개 서비스 계약을 대체하지 않습니다. 추천 수량과 예상 수요는 고정 fixture를 읽고, 프론트엔드가 최적화·위험 판정 알고리즘을 계산하지 않습니다. 비용 합계만 단가×수량으로 표시합니다. 미제공 단가는 0으로 대체하지 않습니다.

- `services/replenishment.ts`: 입고 예정·판매량 추세·과잉 위험·추천·예산 데이터와 초안 생성 인터페이스 **제안**.
- `services/mock/replenishment-data.ts`: 초기 추천/계획 fixture. 예산 100,000원, 추천 합계 88,000원은 데모 정보.
- 기존 mock 서비스의 메모리에 신규 초안을 넣어 기존 발주 상세·수량 저장·승인으로 이어집니다.
- 같은 추천의 중복 초안 생성은 방지합니다. AI 질문만으로 초안이 생성되거나 발주가 승인되지 않습니다.
- 추천 카드에서 확인창을 거쳐 생성한 뒤에도 초안 상태이며 실제 발주를 전송하지 않습니다.
- 승인 실패는 기존 상태를 유지합니다. 승인만으로 재고를 증가시키지 않습니다.
- 입고 예정 수량은 현재 재고와 별개입니다. 입고 등록·DB 반영은 서버 연동 준비 중이며 현재는 입고 내역 조회만 제공합니다.
- 예산 초과는 검토 경고입니다. 서버에 없는 승인 조건을 프론트엔드에서 새로 강제하지 않습니다.
- API 모드에는 신규 계획 서비스도 `contract_pending`을 반환합니다. 오류 시 Mock으로 자동 전환하지 않습니다.
- AI 액션은 허용된 경로/식별자를 검증하며 임의 URL·문장·코드를 실행하지 않습니다. 기존 AgentAction 계약은 보존하고, Mock에서만 선택적 UI 메타데이터를 제공합니다.

Android/iOS 실기기, 네이티브 키보드·시스템 큰 글꼴·스크린 리더, 실제 API·DB·인증·입고 처리는 미검증입니다. Expo 개발 도구의 최신 버전 설치는 로컬 권한 제한으로 실패하여 내장 대체 버전으로 실행됐습니다. 웹 화면·빌드 성공과는 별개이며 패키지나 Python/AI 모델을 설치하지 않았습니다. 이 디자인 작업에 대한 commit/push/merge는 수행하지 않았습니다.

## 실제 API 어댑터 준비 — 현재 실행 모드와 서버 담당자 인계

아래 내용이 이전의 `live=contract_pending` 설명을 대체합니다. 실제 백엔드를 운영하지 않는 현재 개발 환경은 **기본 mock을 유지**합니다. 프론트엔드에 실제 HTTP 조회/AI 어댑터를 추가했으나 실제 서버 연결 성공을 의미하지 않습니다. 서버가 없어도 디자인을 확인하려면 기존처럼 mobile/에서 `npm run web -- --port 8081`을 실행합니다.

서버 주소를 받은 뒤 mobile/.env.example을 .env.local로 복사하고 다음을 설정합니다. .env.local은 Git 제외 대상이며 개인 IP를 공통 코드에 넣지 않습니다.

```dotenv
EXPO_PUBLIC_DATA_SOURCE=api
EXPO_PUBLIC_API_BASE_URL=http://접속가능한서버주소:8000
EXPO_PUBLIC_WAREHOUSE_ID=WH-ASAN
```

API_BASE_URL은 `/api/v1`을 붙이지 않은 서버 루트 주소입니다. 휴대폰에서는 localhost 대신 서버 PC의 LAN 주소 또는 배포 주소를 사용합니다. 수정 후 Expo를 재시작하고 앱을 다시 로드합니다. 설정 화면에서 API 모드·주소·매장을 확인할 수 있습니다. EXPO_PUBLIC에는 비밀번호/운영 키/토큰을 넣지 않습니다. 백엔드가 중단되면 오류와 재시도를 표시하며 Mock으로 자동 전환하지 않습니다. API 주소가 없거나 예제 주소이면 명시적으로 설정 오류를 표시합니다.

**연결 구현:** 대시보드, 재고/상품 상세, 추천, 발주/입고 내역 조회, 오늘까지의 판매 기간 조회, AI 질문 POST. `services/api/services.ts`가 URL·서비스를 연결하고 `decoders.ts`가 unknown 응답을 검증/변환합니다. 기존 contracts 인터페이스를 유지하며, 화면에 없는 정보를 꾸며내지 않도록 발주 품목의 예측/납기/추천·입고 날짜와 판매 갱신 시각, 과잉 판정을 nullable로 확장했습니다. Mock 데이터와 동작은 그대로입니다.

**제한:** 서버의 초안/추천/발행 계약이 모바일과 달라 상품 저장·실사·초안 생성·수량 저장·승인·입고 등록은 API 모드에서 차단합니다. 현재 등록 endpoint가 있더라도 필요한 모바일 필드와 업무 의미가 맞지 않으면 임의 호출하지 않습니다. 발주 API에는 매장 필터가 없어 WH-ASAN 외 발주 조회는 차단합니다. 이는 서버의 인증/매장 권한을 대신하지 않습니다. 바코드/판매 이력/비교 지표/예산/과잉 위험/일부 발주 근거는 서버 미제공으로 표시합니다. 판매 임의 과거 기간 조회는 현재 days 기반 endpoint의 지원 범위 밖이어서 명시적으로 차단합니다.

백엔드 담당자에게 전달할 이유·요청 API·발주 계약·입고 검증·B/C/D 역할·완료 기준은 [BACKEND_HANDOFF.md](./BACKEND_HANDOFF.md)에 정리했습니다. 백엔드/Python/DB/AI 모델을 설치하거나 수정하지 않았고 인증을 가장하지 않습니다.

`npm test`에는 기존 19개(기존 API 차단 테스트는 새 동작에 맞춰 갱신)와 신규 API 어댑터 5개가 있습니다. 테스트 HTTP fixture로 필드 변환, 같은 화면의 중복 요청 공유/새 조회, 오류·잘못된 응답·빈 데이터, 미지원 쓰기 차단, AI 액션·토큰 전달, 판매 기간을 검증합니다. 실제 서버/DB/실기기 연동 테스트는 별도로 필요합니다.

이번 검증 결과: TypeScript·ESLint 통과, 서비스 테스트 24개 통과, Expo 웹 export 및 Android Hermes 번들 생성 성공. 기존 Edge의 Mock POS 회귀 검사도 320~1280px 배치, 검색, 입력 검증, 저장 실패 시 입력 보존, 저장/상세 이동, 초안 확인/취소, 빈 목록/오류/재시도를 통과했습니다. 이는 실제 Android 기기 실행이나 실제 백엔드 통신/DB 저장 성공을 의미하지 않습니다. 신규 의존성·백엔드 수정·commit/push/merge는 없습니다.

### 공유 브랜치 통합 기준

사용자 승인에 따라 이번 모바일 변경을 feat/pos-ui-backend에 공유합니다. 원격 94cc14b의 AI 개선과 백엔드 테스트를 fast-forward로 먼저 반영했고, 기존 로컬 작업 파일 30개의 SHA-256이 그대로 보존되는 것을 확인했습니다. 이번 새 커밋에는 mobile/의 POS UI·API 어댑터·테스트·문서만 포함하며 backend/와 루트 Vite 앱은 원격 기준 그대로입니다. main에는 직접 push하거나 merge하지 않습니다. 이전 절의 commit/push 미수행 문구는 각 작업 완료 당시의 기록입니다.

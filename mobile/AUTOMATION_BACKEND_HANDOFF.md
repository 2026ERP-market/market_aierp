# AI 자동 발주 — 백엔드 담당자 개발 지시문

## 목표와 현재 구현 범위

`mobile/`의 **AI 추천 → 서버 자동 발주 → 발주 내역 → 입고 확인** 흐름을 완성해 주세요. 사장님이 자동화 설정을 명시적으로 켠 매장에 한해 개별 초안 저장·상품별 승인 없이 실행합니다. OFF인 매장은 기존 수량 수정·수동 발주·거절 흐름을 유지합니다. LLM의 문장을 명령으로 실행하지 않고 수요 예측/추천 엔진의 구조화된 결과와 서버 정책을 사용하세요.

프론트엔드 구현:

- 홈의 `샘플 ON` 장식을 `자동 발주` Switch와 설정 창으로 교체했습니다. 샘플/API 출처 문구는 별도로 유지합니다. 설정 페이지에서도 동일한 상태를 사용합니다.
- Mock에서만 기본 OFF, 최초 ON 확인, 현재 미처리 샘플 추천 즉시 발주, 개별 성공/제외/실패, 내역 이동, OFF, 재시도를 지원합니다. 상태는 메모리뿐이며 앱 재시작 시 OFF입니다. 주의 문구가 있는 샘플도 실행되므로 운영 정책 준수나 모델 신뢰도 검증을 뜻하지 않습니다.
- Mock의 ON은 한 번 실행합니다. 이후 `샘플 추천 이벤트 재실행 / 재시도`로 서버 추천 이벤트를 재현합니다. 앱 타이머·백그라운드 작업·실제 모델·공급업체 전송을 구현한 것이 아닙니다.
- 실제 API 모드는 **상태 미확인 / 연동 준비**로 표시하고 Switch를 비활성화합니다. 존재하지 않는 API URL은 호출하지 않으며 Mock으로 대체하지 않습니다.
- `src/services/automation.ts`의 AutomationService가 UI와 실행 구현을 분리합니다. 현재 실제 API 구현은 명시적 미지원입니다. 연동 시 서버 조회/저장 응답을 검증해 상태를 갱신하는 어댑터로 교체해 주세요. `runDemo`는 운영에서 호출하면 안 됩니다.

## 먼저 코드·계약 확인

공유 직전 원격 `4d7f547`의 팀원 변경을 반영했습니다. 현재 `backend/app/api/v1/endpoints/purchases.py`에는 추천 GET, 추천 action POST, 공급업체별 발주 POST, 내역 GET, 입고 POST와 새 `POST /api/v1/purchases/direct-order`가 있습니다. 모바일 `services/api/services.ts`에도 직접 발주 연결이 추가되었습니다. 실제 서버 통신은 이 PC에서 검증하지 않았습니다. 자동화 서버 구현은 새 direct-order의 업무 처리를 검토·재사용하되 매장 권한·정책·멱등성·자동 실행을 별도로 검증하세요. 기존 `/orders` POST는 승인된 공급업체 추천 전체를 발행하므로 상품별 요청으로 임의 호출하지 마세요. `mobile/DIRECT_ORDER_API.md`의 제안 중 이미 반영된 부분은 최신 서버 코드와 대조하세요.

설정·권한·자동화 실행 API와 서버 작업자는 현재 확인한 코드에 없습니다. 아래 주소/필드는 **협의할 제안**이며 기존 서버 계약이 아닙니다. 구현 전에 팀원 B/C/D와 확정하고 모바일 어댑터/응답 검증/테스트까지 연결해 주세요. 기존 로그인·DB·모델·수동 API를 임의 재작성하지 마세요.

## 서버 구현 업무

1. 매장별 자동화 설정을 DB에 저장합니다. 기본 OFF, 서버 인증과 사장님 권한 검증, 활성화 동의 주체·시각·정책 버전을 기록합니다. 지금 앱에는 실제 인증이 없으므로 인증 연동 전 운영 자동화를 허용하지 마세요. 프론트에서 보내는 warehouse_id만 신뢰하지 마세요.
2. 기존 추천 엔진을 재사용해 유효한 새 추천이 확정되는 이벤트에서 서버 작업자/큐로 자동 발주합니다. 앱 실행·화면 조회·LLM 응답·GET 호출이 자동화 트리거가 되면 안 됩니다. 앱이 닫혀도 서버에서 처리합니다. 추천 생성 GET의 기존 부작용과 반복 조회가 중복 실행되지 않도록 분리합니다.
3. ON 저장과 실행 이벤트 생성이 누락되지 않게 트랜잭션/아웃박스 등을 사용합니다. ON 시 현재 미처리 추천도 처리할지 여부를 계약에 명시하세요. 현재 UI는 Mock의 현재 추천도 즉시 처리한다고 안내하므로 실제 활성화 전 안내를 서버 정책에 맞추세요.
4. 추천 상태·정책·설정 버전을 실행 직전에 다시 검증하고, 매장/추천/예측 버전 기준 고유 키와 DB 잠금/트랜잭션으로 중복을 방지합니다. 수동 발주·거절·자동 실행이 경합해도 하나만 성공해야 합니다. 같은 상품의 중복 예측은 기존 미입고 발주까지 고려해 재평가하세요.
5. 추천 원본 수량, 실제 발주 수량, 추천/모델 버전, 판단 근거, trigger=automation, 정책 버전, 자동화 실행 ID를 발주/로그에 남깁니다. 수동 발주와 자동 발주를 서버 내역에서 구분해 내려주세요. 기존 승인 상태를 가짜 사용자 승인으로 기록하지 마세요.
6. 정책은 서버에서 검증합니다: 양의 정수·포장 단위, 활성 공급업체/상품, 매입가·발주 가능 여부, 가용/입고 예정 재고, 소비기한/과잉 위험, 예측 유효기간, 상품별 수량/금액 및 일일 누적 예산 한도. 한도와 허용 상품/공급업체는 서버 정책으로 관리하고 필요한 설정 UI는 팀원 A와 협의하세요. 불완전하거나 위험한 추천은 자동 발주하지 않고 제외 사유와 수동 검토 필요 상태를 제공합니다. 운영 한도 값은 임의로 하드코딩하지 마세요.
7. OFF 응답 이후 새 작업이 발행되지 않도록 실행 직전 원자적으로 설정을 확인합니다. 이미 확정된 발주/외부 전송을 취소하는 기능과 OFF를 구분하세요. 저장 실패/타임아웃 시 앱은 상태 재조회로 확인하고 실패를 성공처럼 표시하지 않습니다. 정책 version/ETag로 여러 기기 간 충돌을 검출하세요.
8. 발주 생성만으로 실재고를 늘리지 않습니다. 입고 예정 수량만 반영하고 기존 입고 처리에서 실제 입고 수량/로트/소비기한을 검증해 재고를 반영합니다. 부분 입고·중복 입고 방지도 유지하세요.
9. 내부 PO 생성과 공급업체 실제 발송은 별도 상태입니다. 발송 연동이 없다면 `발주서 생성`이라고 표시하고 실제 주문 전송 완료로 가장하지 마세요. 외부 호출은 멱등 키·재시도·결과 확인·실패 기록을 갖추세요. 작업 재시작/응답 유실 시 중복 공급업체 주문이 생기면 안 됩니다.
10. 권한 거부·세션 만료·설정 충돌·제외·실행 실패를 구분해 반환합니다. 감사 로그와 실행 결과를 매장별로 조회할 수 있게 하고 키/토큰/개인정보를 로그에 남기지 않습니다. 기존 수동 API는 삭제하지 마세요.

## 필요한 API 계약 초안 — 아직 구현되지 않은 제안

| 기능 | 제안 | 요청/응답에 필요한 의미 |
|---|---|---|
| 상태 조회 | GET `/api/v1/automation/settings?warehouse_id=...` | enabled, warehouseId, version, updatedAt, canManage, policy(한도/대상), workerStatus. 권한 거부를 OFF로 바꾸지 않음 |
| 설정 변경 | PUT `/api/v1/automation/settings` | warehouseId, enabled, expectedVersion, ON 동의/정책 버전. 서버 확정 설정 반환, 저장 멱등성 및 충돌 지원 |
| 실행 기록 | GET `/api/v1/automation/runs?warehouse_id=...&cursor=...` | runId, recommendationId, productId, 모델/정책 버전, 원본/최종 수량, created/skipped/failed/dispatch 상태, reason, orderId, 시각, 다음 cursor |
| 기존 발주 내역 확장 | 기존 내역 API 재사용/호환 확장 | source=manual/automation, automationRunId, recommendationId, 수량 구분, 외부 발송 상태. 기존 앱 필드 호환 유지 |

ON/OFF 설정 조회와 변경은 `AutomationService`의 live 어댑터로 연결하고 unknown 응답을 검증하세요. 현재 스냅샷의 `enabled: null`은 서버 상태 미확인입니다. 로딩/권한 없음/오류/재시도/조회 실패 후 오래된 상태를 표현하도록 필요한 타입 확장을 협의하세요. 토글은 서버 저장 성공 후 확정 상태로 표시하고 중복 저장을 막습니다. UI가 보이는 동안만 결과를 재조회할 수 있으나 실행 자체는 서버가 담당해야 합니다. 운영 실행을 모바일 `placeOrder` 반복 호출이나 `runDemo`로 대체하지 마세요.

## 인수 테스트와 완료 기준

- 기본 OFF이면 추천 조회·생성만으로 발주하지 않습니다. ON 저장 후 새 추천은 개별 승인 없이 서버에서 1회 발주되고 내역에 자동 발주 출처가 표시됩니다.
- 앱 종료/재접속/서버 재시작/두 기기 접속/동일 이벤트 재전송에도 설정이 유지되고 주문이 중복되지 않습니다.
- OFF와 실행 경합, 수동 발주/거절과 실행 경합, 예측 버전 갱신, 처리 중 네트워크 유실, 공급업체 전송 실패 후 재시도를 검증합니다.
- 다른 매장/권한 없는 사용자/세션 만료는 서버가 차단합니다. 한도 초과·불완전한 추천은 제외 사유가 보이고 가짜 성공/Mock fallback이 없습니다.
- 발주 후 현재 재고는 그대로이고 입고 확인 후에만 증가합니다. 기존 수동 발주·조회·입고 기능의 회귀 테스트를 통과해야 합니다.
- 팀원 A의 타입 검사·서비스 테스트·웹 빌드와 실제 Android 기기+실제 서버 E2E를 수행합니다. 미수행 검증은 분리 보고하세요.

이번 프론트 작업은 backend/DB/AI 모델을 수정하지 않습니다. 자동화 운영 완료는 위 서버 작업 및 실제 통합 검증 이후에만 판단합니다. main에 직접 push/merge하지 말고 합의한 작업 브랜치에서 PR로 리뷰하세요.
